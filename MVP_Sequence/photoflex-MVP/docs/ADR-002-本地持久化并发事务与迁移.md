# ADR-002：本地持久化并发、事务与迁移

## 背景

PhotoFlex 网页 MVP 使用 IndexedDB 保存可变工作区、不可变命名版本、照片索引、Source 授权和缩略图缓存。用户可能同时打开多个标签页，未来 Tauri 也可能出现多窗口；同时，IndexedDB 事务具有自动提交和 versionchange 升级语义。如果不明确并发、事务与迁移规则，“冲突”和“原子保存”只会成为无法验证的口号。

## 决定

### 1. 工作区使用整数 revision CAS

- `ProjectWorkspace.revision` 是 ProjectStore 独占写入的工作区级非负单调整数；新项目为 0，每次成功的 `saveWorkspace` 或 `createVersion` 加 1；
- 写事务先读取当前 ProjectWorkspace，只有 `current.revision === expectedRevision` 才写入；否则不改变任何记录并返回包含 expected/actual 的 conflict；
- conflict 不自动 last-write-wins、不合并，也不使用旧 revision 盲重试。调用方暂停保存队列、保留本地未保存状态并要求用户重新加载；
- SequenceDraft 不保存 persistence revision，SequenceEditor 也不负责增长 revision。

### 2. IndexedDB 事务内不执行外部异步工作

- 版本快照在事务外完成构造和校验；
- `createVersion` 使用同时覆盖 `projects` 与 `versions` 的单个 `readwrite` 事务；
- CAS 读取、`versions.add` 和 `projects.put` 只能在事务创建任务或相关 IndexedDB request 回调中排入；事务内禁止文件读取、图片解码、网络、计时器和无关 Promise；
- 只有 transaction `complete` 才返回成功；`abort/error` 返回明确失败。`complete` 是提交证据，不是保持事务活跃的方法；
- 真实 Chromium 测试在版本写入后主动 abort，必须证明两个 object store 全成或全败。

### 3. 三种 schema 独立版本化

- IndexedDB database version 控制 object store/index；
- ProjectWorkspace schemaVersion 控制本地记录形状；
- `.photoflex.json` backup schemaVersion 控制可移植备份格式；
- 当前数据库和 workspace schema 为 2；从 v1 建立顺序 migration runner，并覆盖新库 `0 → 1 → 2` 与旧 workspace `1 → 2` 测试。迁移只追加，不修改已发布步骤；失败时 abort 并保留旧库，不得删除重建；
- 其他标签页收到 `versionchange` 时关闭连接；升级 `blocked` 时提示用户关闭其他标签页；未知更高 schema 禁止降级写入。

### 4. 命名版本保存完整快照

第一阶段的 SequenceVersion 是独立完整快照，不是相邻版本 diff。存储量随版本数和每版项目数按 O(V × S) 增长；自动保存不重写历史快照。M5 测量 200 个版本 × 500 项的数据库占用、Compare 打开时间和备份体积，只有实测表明不可接受时才通过新 ADR 评估压缩、分块或增量链。

## 被否决的方案

- 用时间戳作为 revision：时钟与并发顺序不可靠；
- 用内容 hash 代替 revision：增加计算成本，但仍不能定义冲突后的产品行为；
- 最后写入覆盖：会静默丢失另一标签页或窗口的工作；
- 在一个普通 async 函数中穿插文件读取和 IndexedDB 写入：不能保证事务保持 active；
- schema 变化时删除并重建数据库：违背本地优先工具的数据安全目标；
- 第一阶段保存版本 diff 链：增加恢复、迁移和局部损坏复杂度，当前 500 项上限下收益不足。

## 结果与代价

- 多标签页和未来多窗口的覆盖冲突可被稳定检测，但第一阶段不自动合并；
- IndexedDB 实现需要真实浏览器集成测试，Memory 适配器测试不能替代；
- 每次存储结构变化必须带 migration fixture 和失败恢复测试；
- 完整版本快照实现简单可靠，但必须持续测量版本数量增长后的配额和备份体积。

## 必须保留的证据

1. 双实例从同一 revision 写入时只有一个成功；
2. `versions.add` 后故障注入不会留下孤立版本或错误 versionIds/revision；
3. database schema `0 → 1 → 2`、workspace `1 → 2`、迁移 abort、blocked/versionchange 和未知高版本测试；
4. production build 的真实 Chromium 500 项 Diff benchmark；
5. 200 × 500 完整快照存储与备份基线。
