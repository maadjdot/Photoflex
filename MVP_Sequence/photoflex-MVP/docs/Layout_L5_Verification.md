# Layout L5 实施与验证记录

日期：2026-09-25
分支：`Layout-Develop`

## 已实施

- 正式 Layout PDF 导出：点击按钮先选择质量，确认后提交当前文字和裁切草稿并固定文档快照；按物理页顺序生成同尺寸 PDF，保留空白页。对象按层级绘制，照片使用共用 Fit/Fill 焦点规则并按框裁切，文字使用 `layoutText` 行结果与嵌入的 Noto Sans CJK SC 字体。为兼容 Chrome 的中文显示和复制，采用完整字体嵌入；子集嵌入在本机 Chrome 中只显示了部分拉丁文字，因此没有启用。
- 导出前逐个图像框检查源文件；空框、缺图阻止导出，低于 150 dpi 的照片列为可继续的提示。检查结果显示页码与对象 ID。导出显示逐页进度，可取消；失败保留当前草稿并允许重试。只有生成完整文件后才触发下载。
- 低／中／高档以最高 150／220／300 dpi 对图像框内可见照片区域重采样并编码为 JPEG，Fit 留白保持透明，不遮盖下层对象；原图档对无需 EXIF 旋转的 JPEG 直接嵌入，需旋转的照片逐张解码并重编码。重复照片及相同裁切结果在 PDF 中共用图像资源。保存失败时导出状态说明文件来自当前内存草稿。

## 性能观察

环境：Windows 10、Intel Core i7-13620H（16 逻辑处理器）、16 GiB RAM、Headless Chrome 153、1440×900。使用 `corepack pnpm dev --port 4173 --mode e2e` 启动，随后执行 `node scripts/measure-layout.mjs [页数] [首页对象数]`。脚本在 IndexedDB 建立 500 个 Sequence photo items 与缩略图/预览，用交替横竖尺寸的合成图片测量从路由打开到工作区可见、点击中间页到选中、可见照片条数量及 JS heap。每项只运行一次，数值为观察值。

| 样本 | 打开 | 选页 | 照片条已挂载 | 可见图像框 | JS heap |
|---|---:|---:|---:|---:|---:|
| 50 页、500 photo items | 371 ms | 107 ms | 11 | 当前页对象 | 42.6 MB |
| 200 页、500 photo items | 417 ms | 209 ms | 11 | 当前页对象 | 48.2 MB |
| 1 页、50 对象、500 photo items | 367 ms | 85 ms（重复选当前页） | 11 | 50 张图像均挂载 | 42.3 MB |

这组测试使用合成 SVG 预览和缺失原片，不代表真实照片解码、50 页导出或峰值内存。

### 39 张真实照片样本

用户提供的 `test_photos` 含 39 张 JPEG，原片合计 277,521,711 字节（约 264.7 MiB），尺寸为 4928×3264 或 3264×4928，EXIF 方向均为 1。原片未被改写。`node scripts/measure-layout-real.mjs` 从这批原片生成 512/768 px JPEG 缩略图与预览，在本机 Headless Chrome 中分别打开下列 Layout；每个场景全量重新加载应用，测量一次。500 个 Sequence photo items 循环引用这 39 张原片，因此此项验证了真实图片预览与条目规模，不等同于 500 张不同原片。JS heap 是操作后观测值，不是峰值或浏览器进程总内存。

| 样本 | 打开 | 选页 | 照片条已挂载 | 可见图像框 | JS heap |
|---|---:|---:|---:|---:|---:|
| 50 页、500 photo items、39 张原片 | 494 ms | 131 ms | 11 | 2（当前页及邻页） | 40.5 MB |
| 200 页、500 photo items、39 张原片 | 485 ms | 124 ms | 11 | 2（当前页及邻页） | 76.3 MB |
| 1 页、50 对象、500 photo items、39 张原片 | 594 ms | 55 ms（重复选当前页） | 11 | 50 | 96.1 MB |

`node scripts/measure-layout-pdf-real.mjs` 让正式 Layout PDF 生成模块逐页读取全部 39 张原始 JPEG：生成 39 页、291,372,842 字节的 PDF；用 `pdf-lib` 重新打开后页数为 39。该 Node 进程耗时 1,841 ms，结束时 RSS 约 822 MB。

`node scripts/measure-layout-browser-pdf-real.mjs --pages=50 --browser=chrome --quality=medium` 在浏览器内通过正式的 `preflightLayoutPdf` 和 `exportLayoutPdf` 读取真实原片并下载 PDF，再重新打开验证每页 A4 尺寸、单张图像资源和首张中英文文字搜索。50 页循环使用 39 张原片，在 Chrome 的单次结果如下；这些耗时及 heap 都是操作后观察值，不是峰值或承诺指标。

| 质量 | PDF 字节 | 约合 MiB | 耗时 | 完成后 JS heap |
|---|---:|---:|---:|---:|
| 低 · 150 dpi | 20,182,672 | 19.2 | 9.1 秒 | 164 MB |
| 中 · 220 dpi | 30,588,705 | 29.2 | 9.9 秒 | 194 MB |
| 高 · 300 dpi | 56,536,584 | 53.9 | 10.8 秒 | 253 MB |
| 原图 · 复用重复照片 | 291,376,152 | 277.9 | 7.2–25.5 秒 | 976 MB |

四档的页数、尺寸、图像资源与 PDFium 中英文字搜索均通过。先前原图档未复用重复照片时，同批 50 页为 371,370,640 字节；复用后约缩小 21.5%。单独的 39 页纯照片 Node 测量为 291,372,842 字节、耗时 1.8 秒、结束时 RSS 约 822 MB。用红色底图、蓝色 Fit 照片叠放的浏览器样本，经 PDFium 渲染取样得到红／蓝／红，确认 Fit 上下留白没有被白色覆盖。

`node scripts/verify-layout-folder-export-real.mjs --pages=50 --browser=chrome --quality=medium` 和 `--browser=edge` 在应用 Table 中用浏览器的文件夹选择控件添加 `test_photos`，等待 39 张照片全部进入索引，进入 Layout，打开质量弹窗并确认正式导出。两个浏览器均下载 50 页 PDF，重新打开后每页恰有一张图像。Chrome 的低／高／原图档也分别从应用弹窗完成一页导出。该脚本预先写入测试项目和 Layout 文档；文件夹导入、源文件读取、Layout 页面与按钮下载均走正式应用流程。测试使用浏览器的临时文件夹授权并在同一页面会话中完成；未覆盖刷新后重新授权。

## 结论

L5 的导出功能、四档质量和 39 张样本的应用内导出已实施并通过。用户已确认目标阅读器搜索框能定位文字。如需评估 500 张不同原片的缓存行为，可在后续补充样本；PRD 要求的 500 个 Sequence photo items 已用 39 张真实原片循环组成的条目覆盖。
