# PhotoFlex 项目企划评估与竞品分析

> 评估对象：[[Photoflex-项目idea]]、[[照片管理&排版系統]]  
> 竞品资料核查日期：2026-08-18

## 一句话结论

**这个项目值得继续验证，但不应该以“摄影全流程平台”起步。** 最有机会的定位是：

> **Lightroom / Capture One 之后、InDesign 之前，面向长期摄影项目的本地优先创作编辑器。**

它帮助摄影师把“问题意识—研究—看图—选择—排序—反思—版本比较”连成一个可回溯的过程；它不是另一个修图软件，也不是一个通用白板。

如果只做“照片管理 + 白板 + 简单排版”，会落入 Lightroom、Milanote、PowerPoint 等成熟工具的夹缝；如果把 **多序列版本、照片与文字理由、项目长期记忆、跨阶段连续性** 做到明显更好，则有真实而清晰的产品价值。

## 总体评分

| 维度 | 评价 | 说明 |
|---|---:|---|
| 问题洞察 | 8/10 | 对长期摄影项目的非线性、反复看图和文字思考理解得很准确 |
| 差异化潜力 | 7/10 | “项目过程 + 序列版本 + 反思”有差异，但目前被过多通用功能稀释 |
| 当前范围可行性 | 3/10 | 现企划同时包含 DAM、白板、AI、排版、协作、社区与发布，接近六个产品 |
| 技术可行性 | 7/10 | 核心编辑器可实现；RAW、跨软件同步、无限画布性能和长期 AI 记忆需要谨慎设计 |
| 商业确定性 | 5/10 | 艺术/纪实摄影师痛点深，但市场较窄且价格敏感，需要先验证付费意愿 |

## 我对项目的理解

企划描述了两种入口：

1. **从已有照片中发现项目**：大量旧照片 → 反复看图 → 形成题目 → 选择与排序 → 排版输出。
2. **从问题出发开展项目**：问题意识 → 研究与拍摄计划 → 拍摄和编辑 → 选择与排序 → 排版输出。

两条路径最后汇合到同一套循环：

```text
问题 / 假设 ↔ 研究 ↔ 拍摄 ↔ 看图 ↔ 选择 ↔ 排序 ↔ 文字反思 ↔ 再拍摄
                                                ↓
                                         Dummy / 摄影书
```

因此，PhotoFlex 真正要管理的不是一堆任务，而是三个持续变化的东西：

- **作品状态**：照片、选择、序列、跨页和 dummy。
- **认识状态**：当前问题、发现、矛盾、决定与尚未理解之处。
- **演化历史**：为什么从 A 版变成 B 版，以及哪些判断后来被推翻。

这是企划中最有价值、也最难被通用软件完整表达的部分。

## 值得保留并放大的点

### 1. 从“单张照片”转向“摄影项目”是正确的抽象

大部分照片工具优化的是导入、技术筛选、修图和交付；PhotoFlex 关注的是一组照片如何共同形成意义。这个问题比“再做一个更轻的图库”更独特。

### 2. “Look hard”不是口号，而可以变成核心交互

产品可以把反复观看设计成具体能力：全局照片墙、无界面全屏观看、不同尺度切换、暂时隐藏评分、随机重看、按拍摄批次对照、查看长期未被使用的照片。重点不是 AI 告诉用户哪张好，而是让用户更容易重新看见自己的照片。

### 3. 将文字视为创作材料，而非项目说明附件

日志、memo、研究与“保留/移除这张照片的理由”能让项目的认识过程留下来。这与普通 DAM（数字资产管理，即保存、检索和组织文件的系统）有本质区别。

### 4. 非线性和版本管理是核心需求，不是附加功能

企划明确指出流程会反复。这意味着版本不应只是“自动保存”，而应包括序列分支、命名检查点、A/B 对照、版本差异和决定记录。

### 5. 对 AI 的克制方向是对的

“多提问、少给答案；不代替艺术判断”比自动打分或自动选片更符合目标用户。AI 最适合成为研究助理、档案员和苏格拉底式提问者，而不是摄影比赛评委。

### 6. 已意识到它不是每日工具

这是重要的商业与交互约束。产品应优化“隔两周重新打开后，60 秒内恢复上下文”，而不是追求签到、连续使用天数或每日任务。

## 需要重新考虑的点

### 1. 当前企划实际上包含至少六个产品

1. 本地照片管理 / DAM
2. 创意白板与研究笔记
3. 照片筛选与序列编辑器
4. 摄影书排版器
5. AI 研究与项目记忆系统
6. 发布、评论、社区与专家服务市场

每一项单独都能成为成熟产品。“精简、轻量、流畅、稳定”与这个范围直接冲突。**必须先选择一个用户愿意为了它离开现有工作流的楔子功能。** 推荐的楔子是：

> **可同时创建、保存、比较和解释多个照片序列的项目编辑器。**

### 2. “Lightroom 做不到照片多项目归属”这一前提不成立

Lightroom Classic 的一张照片可以属于多个收藏夹，删除收藏夹也不会删除原文件；它还有智能收藏夹、用户排序、Survey 对比视图、幻灯片和 Book 模块。[Adobe 收藏夹说明](https://helpx.adobe.com/uk/lightroom-classic/help/photo-collections.html)、[浏览与比较说明](https://helpx.adobe.com/ca/lightroom-classic/help/library-module-basic-workflow.html)、[Book 模块说明](https://helpx.adobe.com/au/lightroom-classic/help/create-photo-book.html)

所以 PhotoFlex 不能宣传“无复制地把照片放入多个项目”或“可以排序”本身。真实差异应是：

- 一个项目中并存多个序列分支，而非复制收藏夹后靠命名管理；
- 并排比较两个版本并显示增删、移动与节奏变化；
- 序列中可保留空位、跨页、章节、文字卡和拍摄缺口；
- 每个判断能连接到 memo、研究来源和后续拍摄；
- 保存整个项目状态，而不只保存照片顺序。

### 3. “项目制”也不是独占概念

Capture One 已有 Projects、Albums、Smart Albums 和 Groups，也支持引用原文件以及一张照片进入多个 Album。[Capture One Catalog 说明](https://support.captureone.com/hc/en-us/articles/360002492217-An-overview-of-Catalogs)

因此竞争点不能是有没有名为 Project 的容器，而是这个 Project 是否表达了摄影项目独有的认识和编辑过程。

### 4. “简化版 Milanote”仍可能是一个很大的坑

Milanote 已能在自由画布中混合图片、笔记、链接、文件、评论、分享和 PDF 导出，也明确面向摄影师和创意项目。[Milanote 产品说明](https://milanote.com/product)、[Moodboard 功能](https://milanote.com/product/moodboarding)

若 PhotoFlex 复制无限画布、连线、任意卡片和多人协作，会花大量时间追赶基础体验。更合理的方案是 **有类型的摄影画布**：只提供照片、文字、来源、联系表、序列、布局和检查点等少数节点；自由度有限，但每种节点都真正理解摄影工作流。

### 5. 排版边界仍需进一步收紧

PowerPoint、Lightroom Book、BookWright、SmartAlbums、Fundy 与 InDesign 都覆盖部分排版。Fundy 已把自动相册设计和在线 proofing（校样反馈）结合；Pixellu 也提供 SmartAlbums 与 Cloud Proofing。[Fundy 功能](https://www.fundydesigner.com/)、[Pixellu 产品](https://www.pixellu.com/)

PhotoFlex 的排版应服务于“验证照片之间的阅读关系”，而不是印刷生产：

- 要做：单双页切换、图片位置和尺寸、留白、简单文字、翻页预览、PDF dummy。
- 暂不做：复杂字体系统、母版、CMYK、专色、印前检查、印厂规格和完整 InDesign 替代。
- 后续高价值出口：导出带原图链接和页面几何信息的清单；验证需求后再考虑 IDML，而不是首版就做。

### 6. “社区”不是功能，而是第二家公司

Behance 已有巨大的创意项目展示网络；Glass 专注摄影社区；PhMuseum 同时经营策展、摄影教育、摄影书课程、作品集点评与导师咨询。[Behance 介绍](https://www.behance.net/about)、[Glass](https://glass.photo/)、[PhMuseum 介绍](https://phmuseum.com/about)

PhotoFlex 的社区若只是公开作品、点赞和评论，很难冷启动，也会稀释创作工具。更可行的起点是：

1. 私密分享某个序列版本；
2. 反馈必须落到具体跨页、照片或问题；
3. 作者能把反馈标为采纳、暂缓或拒绝，并生成下一版本；
4. 后期再邀请少量导师做付费 review。

先建立高质量反馈协议，再考虑公开 feed。

### 7. 目标用户需要更尖锐

当前描述不适合“所有摄影师”。不同人群的需求和付费动机并不相同：

| 人群 | 痛点匹配 | 付费能力 | 现有竞品 | 建议 |
|---|---:|---:|---|---|
| 艺术 / 纪实 / 长期项目摄影师 | 很高 | 中低 | 工具分散，常靠人工工作流 | **首要用户** |
| 摄影专业学生、工作坊学员 | 很高 | 低，但机构可付费 | Milanote、PPT、打印小样 | **与院校/导师场景一起验证** |
| 摄影编辑、策展人、导师 | 高 | 中高 | 视频会议、PDF 批注、Milanote | **重要的协作端与付费端** |
| 婚礼 / 人像工作室 | 中低 | 高 | Fundy、SmartAlbums、Aftershoot | 暂不主攻；其核心是效率、销售和客户交付 |
| 大型商业创意团队 | 中 | 高 | Kive、DAM、Adobe 生态 | 首版不主攻，协作和权限要求过重 |

推荐的初始 ICP（理想客户画像）是：**正在进行 3 个月以上艺术/纪实项目、经常与导师或编辑讨论、目前用 Lightroom + PPT/Milanote/打印小样管理多个版本的人。**

## 竞品比较：真正的对手是一套组合

| 竞品 / 替代方案 | 已经做得好的部分 | PhotoFlex 不能再声称的优势 | 仍可切入的空档 / 应学习之处 |
|---|---|---|---|
| Lightroom Classic | 文件夹、收藏夹、智能筛选、评分、Survey、用户排序、幻灯片、Book | 多收藏夹、排序、照片书预览 | 研究与 memo、跨阶段状态、多序列并排比较、决定历史；学习其引用原件和快捷筛选 |
| Capture One | Catalog / Session、Project / Album、引用文件、编辑 | “项目制”和无复制分组 | 摄影问题意识、序列分支和长期反思；学习其 Project 层级 |
| Photo Mechanic Plus | 快速浏览、联系表、虚拟 Collection | 快速看大量照片 | 不与其比导入速度；学习键盘优先和大图库性能。[Collection 说明](https://docs.camerabits.com/support/solutions/articles/48001078321-collections-in-photo-mechanic-plus) |
| Milanote | 研究、视觉白板、图片+文字、分享评论 | 自由白板、moodboard、研究收集 | 做摄影专用节点、序列和版本，而非通用画布 |
| Kive | AI 视觉搜索、相似图、Boards、资产版本、评论与活动记录 | “AI 找图 + visual library + board” | 强调本地原件、非生成式摄影、艺术项目语境；学习自然语言检索和资产关系。[Kive Library/Boards](https://kive.ai/docs/library-asset-management/library-and-boards)、[视觉搜索](https://kive.ai/docs/library-asset-management/search-your-library) |
| Narrative Select / Aftershoot | AI 技术筛片、闭眼/失焦判断、批量修图和交付 | AI 辅助选片 | **刻意不做艺术排名**；学习“AI 建议可被忽略”的交互。[Narrative Select](https://narrative.so/select/lessons/quickstart-guide)、[Aftershoot](https://aftershoot.com/roadmap-2026/) |
| SmartAlbums / Fundy / BookWright | 快速相册排版、印厂衔接、客户 proofing | 相册排版和反馈本身 | 在进入正式排版前解决主题、顺序和版本；学习 spread-based（以跨页为单位）的反馈 |
| InDesign | 专业排版、印刷控制、分享审阅 | 自由排版和专业输出 | 只做创作预演并顺畅交接；不要取代它。[InDesign Share for Review](https://helpx.adobe.com/uk/indesign/using/share-for-review.html) |
| Behance / Glass / PhMuseum | 展示、发现、摄影社群、策展、教育和导师 | 公开展示或评论社区 | 以“过程版本 + 有结构的 critique”区别，社区延后 |
| Notion / Linear | 类型化对象、关联视图、状态、活动记录、快速导航 | 项目看板 | 学习数据模型和状态恢复，不照搬任务管理 UI |

**最危险的替代品不是某一个软件，而是摄影师已经习惯且几乎不增加成本的组合：Lightroom + 文件夹 + Milanote/PPT + InDesign + 通用 AI。** PhotoFlex 必须让其中至少一个高痛点步骤提升一个数量级，而不仅是把这些功能放进同一窗口。

## 对企划问题的逐项回答

### 问题 1：Lightroom 收藏夹已经很强，PhotoFlex 的优势是什么？照片管理做到什么程度？

#### Lightroom 已经能做的

- 同一照片进入多个收藏夹而不复制原件；
- 收藏夹集合、智能规则、评分、颜色和标签；
- Grid、Compare、Survey 和第二显示器；
- 普通收藏夹中的自定义排序；
- 复制收藏夹以手工保存另一顺序；
- 幻灯片、联系表、Book 和 PDF/JPEG 输出。

#### Lightroom 缺少或不是第一等对象的

- 一个序列的多个分支及并排差异；
- 空位、章节、文字卡、跨页节奏和“待补拍”位置；
- 照片选择与研究、memo、问题、反馈之间的关系；
- 项目级的命名检查点与版本演化；
- “上次做到哪里、为什么这样改”的恢复机制；
- 面向导师/编辑的过程反馈，而不只是成品评论。

#### 推荐的功能边界

PhotoFlex 只做 **项目内照片引用层**，不做完整 DAM：

- 读取文件夹、缩略图、基础 EXIF、评分和颜色；
- 建立代理图缓存，原文件不移动、不改名、不上传；
- 允许项目内标签、分组、联系表和快速筛选；
- 提供断盘提示、路径重连和基于指纹的找回；
- 不做 RAW 显影、镜头校正、复杂关键词体系、全盘去重和文件清理；
- 首版不直接修改 Lightroom catalog。

### 问题 2：不打乱 Lightroom 编辑工作流，PhotoFlex 应如何定位？

定位为 **companion app（伴随式应用）**，而不是迁移目的地。

推荐工作流：

```text
Lightroom 中修图与初筛
        ↓
“Send to PhotoFlex”插件 / 选择引用文件夹
        ↓
传递：文件路径、Lightroom UUID、评分、颜色、拍摄时间、编辑后 JPEG 代理图
        ↓
PhotoFlex 中做项目研究、联系表、序列、版本和 dummy
        ↓
导出 PDF / 文件清单 / 顺序；后期可回写收藏夹或项目关键词
```

Adobe 官方 Lightroom Classic SDK 支持插件读取照片对象和元数据、请求 JPEG 缩略图、增加菜单以及定制导出/发布流程，技术上适合做桥接。[Lightroom Classic SDK](https://developer.adobe.com/lightroom-classic)、[SDK 的 LrPhoto 能力](https://archive.stecman.co.nz/files/docs/lightroom-sdk/API-Reference/modules/LrPhoto.html)

实现顺序建议：

1. **MVP：引用文件夹/JPEG 导出目录。** 最快、跨软件，但无法完整获得 Lightroom 编辑状态。
2. **推荐正式方案：Lightroom Classic 插件。** 传递选择、稳定 ID、代理图和元数据；PhotoFlex 仍不碰原件。
3. **后期：Lightroom Cloud API。** 服务云端 Lightroom 用户，但不要让首版同时承担两套 Adobe 架构。

不要直接读写 `.lrcat` 数据库；这是脆弱且高风险的耦合。若需共享通用元数据，可选择用户主动从 Lightroom 写入 XMP，但 PhotoFlex 自身仍应默认只读。[Adobe XMP 说明](https://helpx.adobe.com/ca/lightroom-classic/help/metadata-basics-actions.html)

### AI 是否必要？能否成为竞争优势？难度如何？

#### 结论

- **对 MVP：不必要。** 没有 AI，序列版本和项目恢复仍应成立。
- **对中期差异化：有价值。** 前提是 AI 建立在结构化项目记忆上，并严格限制为检索、整理和提问。
- **真正难的不是调用模型，而是让 AI 知道什么发生过、证据在哪里、何时应该闭嘴。**

推荐 AI 角色：

| 角色 | 可以做 | 不应该做 |
|---|---|---|
| 研究助理 | 搜索艺术家、历史语境、地点与概念，提供来源和相反观点 | 无引用地编造摄影史或替用户确立主题 |
| 项目档案员 | 总结本次变化、找回旧 memo、列出尚未解决的问题 | 把摘要当成原始记录并覆盖用户文字 |
| 苏格拉底式编辑 | 根据用户的选择追问“为什么”“有何证据”“什么照片缺失” | 给照片打艺术分、自动宣布最佳序列 |
| 检索助手 | 用自然语言找到“所有关于边界但没有人的照片” | 静默上传全部原图或把机器标签当事实 |
| 流程助手 | 建议下一次可执行动作、生成拍摄清单草案 | 用任务提醒绑架非线性创作 |

竞争优势不会来自“接入某个大模型”，因为竞品也能接入；会来自 **摄影项目的数据结构、长期记忆、提问协议和用户对 AI 边界的信任**。

### 摄影研究：通用 AI 是否够用？是否需要训练知识库？

推荐分四层递进：

1. **通用模型 + 联网检索 + 强制引用：首版足够。** 可完成概念地图、关键词扩展、艺术家/作品线索和来源摘要。
2. **用户项目资料库：从第一天就要。** 用户保存的网页、PDF、memo、采访和拍摄日志应可检索，这是最相关的知识。
3. **策展式摄影知识库：验证需求后建设。** 收录有授权或可合法使用的访谈、展览文本、艺术家陈述、摄影理论目录与机构资料，并保存出处。
4. **微调（fine-tuning）：最后再考虑。** 微调适合调整提问风格和输出格式，不适合代替可更新、可引用的知识库。

也就是说，摄影方向的优势主要来自 **RAG（检索增强生成：先从资料库取回相关原文，再让模型基于它回答）与编辑策展**，而不是先训练一个“懂摄影”的大模型。

### AI 视觉成本会很高吗？是否必须接视觉模型？如何定价？

#### 成本判断

视觉成本不一定高；**把几千张原图反复发送给最强模型** 才会高。应使用分层架构：

1. **零云成本层**：本地生成缩略图、读取 EXIF、感知哈希去重。
2. **本地视觉向量层**：用 CLIP / SigLIP 一类模型对小缩略图生成 embedding（语义向量），实现相似图和初步自然语言检索；每张图只计算一次。
3. **低价批处理层**：用户明确同意后，对缩略图一次性生成可编辑的描述/标签。
4. **高质量理解层**：只有用户选中的少量照片或当前序列才交给高能力视觉模型，用于提出问题和发现关系。

大模型通常按输入/输出 token 计费，图像分辨率、数量、模型档位和是否重复传入都会影响成本；长上下文还会增加延迟。当前官方定价已经提供低价批处理与缓存机制，但价格会变化，产品不能写死成本假设。[Gemini API 定价](https://ai.google.dev/gemini-api/docs/pricing)、[批处理与缓存优化](https://ai.google.dev/gemini-api/docs/optimization)

#### 产品定价建议

由于这是“项目节点型”而非每日工具，不建议只卖月订阅：

- **Core**：本地项目、序列和版本；一次性买断或低价年费。
- **AI Credits**：按项目包或额度付费，扫描前显示预计用量；允许用户关闭云端视觉。
- **BYOK**：高级用户可填自己的模型 API key，降低平台成本和定价焦虑。
- **Mentor / Studio**：导师协作、私密 review、班级项目和存档按席位年费。

首版不要承诺“无限 AI”。对未发表照片默认本地处理、代理图上传必须明确授权，并让用户可以删除云端数据。

### 如何实现 AI 的项目长期记忆？

**长上下文不等于长期记忆。** 模型的一百万 token 窗口更像一次会话的“大工作台”；长期项目仍需要数据库、检索和版本。官方长上下文文档也把 context window 类比为短期记忆，并指出更长输入会带来成本、延迟和检索准确度权衡。[Gemini 长上下文说明](https://ai.google.dev/gemini-api/docs/long-context)

推荐的数据结构：

1. **Canonical Project Brief**：用户确认的当前项目问题、边界、术语与禁区；不由 AI 静默修改。
2. **追加式事件日志**：导入、选择、移除、移动、写 memo、建立版本、收到反馈等都记录时间与对象。
3. **类型化对象图**：照片、拍摄、来源、问题、memo、序列、布局、反馈和版本都有 ID，并通过关系连接。
4. **会话摘要**：每次结束生成“做了什么 / 为什么 / 未决问题 / 下次入口”，用户可编辑确认。
5. **向量索引 + 结构化查询**：语义检索负责“意思相近”，数据库负责日期、版本、作者和准确关系。
6. **版本快照**：检查点保存项目状态；原始日志不被摘要覆盖。
7. **Context Builder**：每次只组合当前选中节点、项目 brief、相关旧记录和必要图片，而不是把全部历史塞给模型。

记忆界面还应提供：`固定为项目事实`、`仅供参考`、`忘记此项`、`查看 AI 使用了哪些记录`。可见性比“模型好像记得”更重要。

### 如何让 AI 理解非线性创作空间？

不要让 AI “看整块画布截图并猜”。让画布底层本来就是图结构：

```text
节点：Photo / Memo / Question / Source / Shoot / Sequence / Layout / Feedback / Checkpoint
边：supports / contradicts / inspired-by / selected-in / removed-from / responds-to / supersedes
```

当用户选中一个序列问 AI 时，系统取回该序列、与它关联的 memo、上一个版本差异和当前核心问题。AI 的回答应引用具体节点，例如“根据 Memo-18 与 Sequence-v4……”，用户可以点击跳回来源。

AI 参与非线性空间的正确方式是 **读取相关子图、指出联系、提出问题**，而不是替用户重新排整块画布。

### 日志、memo 和反思如何引导？

采用三层设计，避免把创作变成填表：

1. **随手记**：任何照片、序列、来源旁都可一键写一句话或录音转文字。
2. **阶段检查点**：用户主动保存版本时，出现 2–3 个可跳过的问题。
3. **AI 追问**：只在用户请求或明显完成一个阶段时出现，并限制问题数量。

推荐提示语：

#### 开始一次工作时

- 今天希望更清楚哪个问题？
- 这次先不处理什么？

#### 拍摄后

- 现场发生了什么与你原先想象不同？
- 哪张照片打开了新的方向？哪种照片一直拍不到？
- 这次拍摄支持还是反驳了原先的问题？

#### 选择照片时

- 保留它是因为它本身强，还是因为它在序列中承担作用？
- 如果移除这张，项目失去什么？
- 这张是否只是重复说明前一张已经说过的内容？

#### 保存新序列时

- 与上一版相比，最重要的变化是什么？
- 这版希望观者在哪一处停顿、困惑或改变理解？
- 当前缺的是一张照片，还是一个尚未想清楚的问题？

#### 暂停项目时

- 目前确信什么？仍怀疑什么？
- 下次回来时，最小的进入动作是什么？

不要用连续签到、强制日报或“完成百分比”。衡量项目不应只靠完成度，也可显示：最后一次关键决定、当前活跃序列、未解决问题和下一次可进入点。

### 白板和照片排序应如何设计？

推荐把“项目地图”和“序列编辑器”分成两个互通模式，而不是在同一无限画布上承担所有操作。

#### 项目地图

- 少量类型化节点；
- 照片与文字可以连线；
- 联系表与序列可折叠成一个节点；
- 支持研究来源、拍摄批次和问题卡；
- 适合看关系，不追求像 Figma 一样任意设计。

#### 序列编辑器（核心）

- 从多个文件夹、收藏夹或联系表拖入；
- 自由拖动、键盘移动、批量插入/移除；
- 可留空、插入章节与 memo；
- 单张流、双页 spread、墙面总览三种视图；
- 保存为命名版本并分支；
- A/B 并排、同步滚动、突出显示增删移动；
- 序列折叠为卡片后可放回项目地图；
- 大量缩略图使用虚拟列表和分级缓存，避免无限画布一次渲染所有原图。

这会比“先做一个自由白板，再往上加摄影功能”更容易形成差异。

### 排版部分应该做到什么程度？

定位为 **dummy / 阅读模拟器**：

- 页面尺寸、单双页、白底为主；
- 图片自由移动、缩放、裁切与对齐；
- 少量文字框和页码；
- 翻页、快速播放、墙面总览；
- 同一序列尝试多个版式；
- PDF 和低清分享链接；
- 导出页面清单、源文件路径与几何信息，方便进入 InDesign。

首版不做复杂印刷。若用户最终仍要进入 InDesign，这不是失败；**PhotoFlex 的价值是帮助用户在进入昂贵的精排阶段前，先把内容与节奏想清楚。**

### 如何实现类似 Notion / Linear 的项目管理？

应学习它们的“类型化对象、关联视图、状态和活动历史”，不要照搬任务看板。

#### 对象层级

```text
Project
├── Core Question / Project Brief
├── Research Sources & Notes
├── Shoots
├── Photo Pools / Contact Sheets
├── Selections
├── Sequence Branches
├── Layout Dummies
├── Feedback Threads
└── Checkpoints / Versions
```

#### 项目状态

状态只用于导航，不作为线性关卡：`探索中 / 拍摄中 / 编辑中 / 排序中 / Dummy / 反馈中 / 暂停 / 已发布`。同一项目可以同时有“继续拍摄”和“测试第三版序列”两个活跃方向。

#### 项目首页

- 当前核心问题；
- 活跃序列与最近一次视觉缩略图；
- 最近三个关键决定；
- 未解决问题 / 待补拍线索；
- 上次会话摘要；
- 下一次最小进入动作；
- 项目时间线与版本图。

Linear 的 issue 在这里不应只是“任务”，还可以是 **一个未决问题或创作假设**；Notion 的 database view 在这里则对应同一批照片或 memo 的不同视图。项目管理服务于恢复创作语境，而不是要求艺术家按流水线完成阶段。

## 推荐的产品定位

### 对外一句话

> **PhotoFlex 是为长期摄影项目设计的视觉编辑工作台：在不移动原片、不替你做艺术判断的前提下，连接研究、照片、序列、反思与版本。**

### 它是什么

- 摄影项目的“Scrivener”：像长篇写作软件管理章节与草稿一样管理照片项目；
- Lightroom / Capture One 的伴随层；
- 以序列和项目记忆为中心的本地优先工具；
- 导师、编辑与摄影师共同讨论作品过程的空间。

### 它不是什么

- 不是 RAW 编辑器；
- 不是更便宜的 Lightroom；
- 不是通用白板；
- 不是完整 InDesign 替代；
- 不是 AI 自动选出“好照片”的工具；
- 首先也不是公开摄影社交网络。

## 建议的 MVP

### 必须有（P0）

1. 本地引用文件夹与稳定缩略图缓存，绝不改动原件；
2. Project、Photo Pool、Contact Sheet 三个基础对象；
3. 高性能看图、筛选和全屏 “Look hard” 模式；
4. 序列编辑器：空位、文字卡、单双页、墙面总览；
5. 序列命名版本、分支、A/B 比较与差异高亮；
6. 照片/序列旁 memo，检查点时生成会话摘要；
7. 项目首页与“上次做到哪里”；
8. PDF dummy、序列清单和源文件路径导出。

### 验证后加入（P1）

- Lightroom Classic “Send to PhotoFlex” 插件；
- 项目研究助手：联网检索、引用来源、问题地图；
- 本地视觉向量搜索与相似图；
- 私密分享某一序列版本，并对具体照片/跨页留言；
- 可选择回写 Lightroom 收藏夹或项目关键词；
- 简单版式预览。

### 后期再做（P2）

- 策展式摄影知识库；
- 导师/编辑付费 review；
- IDML 或更深的 InDesign 交接；
- 公开项目档案与小规模策展社区；
- 团队权限、院校班级和机构管理。

### 明确不进入首版

- RAW 显影与调色；
- AI 艺术质量评分或自动“最佳序列”；
- 完整无限白板；
- 完整印前与印厂下单；
- 社交 feed、点赞排行和开放社区；
- 同时支持所有 DAM 的深度双向同步。

## 开发前最值得验证的假设

在写大量代码之前，找 8–12 位目标用户，让他们直接展示一个正在进行的真实项目，而不是只问“你会不会用”。重点观察：

1. 他们目前如何保存第二、第三套序列？
2. 两周后重新打开项目时，最难找回的是什么？
3. 哪些信息在 Lightroom、PPT、纸样、聊天记录之间丢失？
4. 他们是否愿意把一个真实项目交给本地引用式新工具？
5. A/B 序列比较能否把一次 30 分钟的工作降到 5 分钟？
6. 他们愿意为本地核心、AI 项目包或导师协作中的哪一项付费？

### 比 DAU 更适合的早期指标

- 首次从 Lightroom/文件夹建立项目所需时间；
- 创建第二个序列版本的比例；
- 使用 A/B 比较后保存新检查点的比例；
- 隔 7–30 天重新打开后，恢复工作所需时间；
- 每个活跃项目的关键会话数，而不是每日活跃用户；
- 原文件误改/丢失事件必须为 0。

## 最终评价

### 正面

这份企划最可贵之处，是它来自真实的创作过程，而不是从“AI + 摄影”倒推功能。它理解长期摄影项目并非线性任务，也意识到文字、版本和反复观看与照片本身同等重要。“AI 不给艺术答案”尤其是一个值得坚持的产品伦理。

### 负面

目前的企划仍把太多正确愿望同时当成首要功能，而且低估了 Lightroom、Capture One、Milanote 与现有排版/反馈工具已经覆盖的能力。如果按现有清单直接开发，很可能得到一个每部分都能用、但没有一部分强到值得迁移的综合工具。

### 最重要的重新选择

不要先证明“我能把整个流程放进一个软件”；先证明：

> **当摄影师需要看懂自己的照片、比较不同叙事并在几个月后继续思考时，PhotoFlex 比 Lightroom + PPT/Milanote 明显更好。**

如果这个命题成立，AI、排版、反馈和社区都能围绕它自然生长；如果它不成立，增加更多功能也不会形成竞争优势。
