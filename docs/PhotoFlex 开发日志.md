### 本次目标

把已认可的新定位转化为可执行的产品功能、技术方案、开发阶段与日志制度。

### 开始前

- **为什么现在做**：产品定位已经收窄，需要在编码前明确功能边界、数据安全和阶段出口，避免再次演变为“全流程平台”。
- **成功标准**：每个核心模块都有实现思路和验收标准；开发路线能明确告诉下一步做什么、何时算完成。
- **明确不做**：不创建软件代码、不初始化 Git、不把 AI/社区提前加入 MVP。

### 验证

- **性能/安全**：仅定义目标和威胁边界，尚未运行 benchmark；不能标记为已验证。

### 决策与权衡

#### D-001：核心楔子

- **决定**：MVP 核心是 Look Hard + 多序列版本 + A/B 比较 + 修改理由 + 上下文恢复。
- **原因**：这是相对 Lightroom + PPT/Milanote 最可能产生明显优势的闭环。
- **未选方案**：从 DAM、通用白板、AI 或社区开始。
- **重看条件**：5 位以上真实用户无法证明多版本序列痛点。

#### D-002：桌面与本地优先

- **决定**：核心产品是本地桌面应用，原片只读引用；云端与 AI 可选。
- **原因**：照片规模、未发表作品隐私、离线需求和现有 Lightroom 工作流。
- **未选方案**：首版浏览器 SaaS、默认上传原图。
- **重看条件**：目标用户明确更需要跨设备协作，且愿意上传代理资产。

#### D-003：Tauri 暂定，保留 Electron fallback

- **决定**：暂定 Tauri 2 + React/TypeScript，但先进行两周技术反转测试。
- **原因**：Tauri 更符合轻量、文件权限和 Rust 后台任务；Electron 更易开发且渲染一致，因此不能在未验证时排除。
- **未选方案**：直接锁死某个框架。
- **重看条件**：六项技术门中有两项无法稳定通过。

#### D-004：版本用不可变完整 snapshot

- **决定**：MVP 保存完整序列 snapshot，并保留轻量事件差异。
- **原因**：序列规模有限；完整 snapshot 更容易恢复、比较、测试和导出。
- **未选方案**：仅存 patch、完整 event sourcing、自动 branch merge。
- **重看条件**：真实项目版本量导致不可接受的空间或性能问题。

#### D-005：RAW 不进入 P0

- **决定**：P0 以 Lightroom/JPEG 代理和常见渲染格式为主；RAW 只读预览放 P1。
- **原因**：RAW 解码、色彩和相机兼容会显著扩大首版风险，而目标用户已有 Lightroom。
- **未选方案**：首版直接显影所有 RAW。
- **重看条件**：用户测试显示没有 RAW 直读就无法采用产品。

#### D-006：AI 不作为 MVP 依赖

- **决定**：P0 的摘要、检索和恢复在无 AI 情况下成立。
- **原因**：避免网络、成本和艺术判断污染核心价值。
- **未选方案**：AI 自动选图、命名主题或生成最佳序列。
- **重看条件**：核心成立后，再验证文本研究、会话摘要与本地检索。

### 结果

- **已完成**：产品与技术企划、开发路线、日志制度。
- **未完成/已知问题**：没有用户访谈数据、没有技术 benchmark、没有代码或安装包；所有技术选择仍属于待验证方案。
- **下一步**：开展 Phase 0，而不是直接实现完整产品。
