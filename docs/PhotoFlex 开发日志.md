## 2026-08-18 · Session 006 · 可调工作区、沉浸观看与单图预览

**阶段**：Phase 0 用户验证<br>
**状态**：completed<br>
**关联 Issue/PR**：无；反馈来源为 comment.md 的“改动意见3”

### 本次目标

让 Sequence + Pool 工作区适应照片数量与不同屏幕使用习惯，并补齐不受编辑界面干扰的序列观看和单图连续预览。

### 开始前

- **为什么现在做**：固定宽度的 Pool 不适合大量候选照片；Sequence 模块、横向画布与单张照片尺寸耦合；用户缺少沉浸阅读和逐张检查入口。
- **成功标准**：两个模块的位置和大小可分别调整；单张照片和横向画布尺寸互不影响；沉浸模式只显示序列；点击照片后可用界面箭头或键盘方向键按序观看。
- **明确不做**：不持久化布局，不接入真实图片，不实现生产级窗口管理、图片解码或大量缩略图虚拟化。

### 实际过程

- 在 Sequence 工作区加入布局调整面板，分别控制 Sequence / Pool 的 X、Y、宽度和高度；
- Pool 模块在固定尺寸内独立滚动，为大量候选照片保留空间；
- 每张 Sequence 卡片加入独立的缩小/放大控制，范围为 120–360px；
- 横向画布高度使用独立状态和滑杆，不随单张照片大小变化；
- 加入沉浸模式，隐藏项目头部、阶段导航、Pool、保存和版本区域，只保留照片序列与退出入口；
- 点击 Sequence 或沉浸序列中的照片可打开大图预览；界面箭头与键盘左右键按当前 Sequence 顺序浏览，Esc 关闭；
- 增加布局、沉浸和大图预览验收预置 URL，并更新 README、访谈任务和预览图。

### 验证

- **语法检查**：app.js 与 smoke-test.js 通过 node --check；
- **自动流程**：新增覆盖模块位置/宽度状态、单图尺寸与画布解耦、沉浸模式隔离、大图按钮、键盘左右键和 Esc；原有 Pool、排序、版本与 Compare 流程继续通过；
- **视觉检查**：1440×1000 下渲染默认 Sequence、布局调整、沉浸序列和单图大图；首次检查发现 315px 画布会截断新增的卡片控件，修正默认值为 350px 后复查通过；
- **已知边界**：布局参数只在当前内存中保留；窄于 850px 时回退为上下堆叠模块，避免百分比自由定位造成不可用。

### 决策与权衡

- **决定**：模块位置使用显式 X/Y 滑杆，照片排序继续使用拖曳；两套手势不复用。
- **原因**：模块与照片都采用直接拖曳时容易争抢手势，用户难以判断是在移动模块还是排序照片；显式布局参数也更容易在访谈中复现。
- **未选方案**：让整个模块自由拖曳、用浏览器原生 resize 手柄、单一全局缩略图尺寸、沉浸模式继续显示完整阶段导航。
- **以后何时重看**：用户认为 X/Y 参数过于技术化、强烈尝试拖动模块标题，或访谈中需要跨会话保留个人布局时。

### 结果

- **已完成**：改动意见3的四类交互、自动回归、四状态视觉验收和访谈说明更新；
- **未完成/已知问题**：尚未用 50–500 张真实候选照片验证 Pool 滚动和布局性能；
- **下一步**：让受试者自行布置工作区并完成一次“排序 → 沉浸观看 → 单图检查”任务，记录其第一反应和调整顺序。

## 2026-08-18 · Session 005 · Sequence 双视角与版本包

**阶段**：Phase 0 用户验证<br>
**状态**：completed<br>
**关联 Issue/PR**：无；反馈来源为 comment.md 的“改动意见2”

### 本次目标

压缩原型的界面密度，为 Sequence 增加横向与网格双视角，并建立可命名保存、可从版本包切换比较对象的版本机制。

### 开始前

- **为什么现在做**：上一轮单一 B 方案方向已确认，但顶部和主标题占用空间过多；长 Sequence 缺少专用横向观看方式；多个历史版本也没有快速切换入口。
- **成功标准**：横向视角默认启用并真实产生溢出滚动；网格视角可切换；Pool 缩窄后保持两列；自定义版本名出现在版本模块和版本包中；版本包能切换星标对比对象。
- **明确不做**：不增加持久化、版本删除/重命名管理、数据库或生产级虚拟列表。

### 实际过程

- 将顶部区域高度从约 108px 缩到约 84px，阶段按钮同步收窄；
- 将 Contact Sheet、Sequence + Pool、Compare 主标题统一缩到约 38px；
- Sequence 增加横向与网格视角切换，默认横向单排；
- 横向视角加入原生底部滚动条、左右滚动按钮和平滑滚动，照片不自动换行；
- 将 Pool 右栏从 430px 缩至约 290px，继续保持两列；
- 在保存区加入版本名称输入框，空名称使用默认 Version N，自定义名称写入不可变版本快照；
- 在 Compare 标题右侧加入 Saved versions 版本包；星标版本作为固定基准，点击任意非星标版本包会切换另一个放大比较位；
- 为验收增加横向、网格和三版本 Compare 预置状态，更新 README 操作路径、访谈问题和四张预览。

### 验证

- **语法检查**：app.js 与 smoke-test.js 通过 node --check；
- **自动流程**：测试覆盖默认横向视角、左右滚动、网格切换、Pool 同步、拖曳排序、自定义名称保存、三版本包、星标固定基准、版本包切换、Memo 和工作副本；
- **视觉检查**：1440×1000 下实际渲染 Contact Sheet、六张横向 Sequence、六张网格 Sequence 和三版本 Compare；
- **滚动验证**：横向预置中第六张照片超出容器，底部滚动条与左右箭头同时可见，未发生自动换行；
- **已知边界**：原生滚动与拖曳尚未在触控板、触屏和大量照片下做性能测试。

### 决策与权衡

- **决定**：横向单排是 Sequence 默认视角，网格是观察全局结构的辅助视角；版本包只选择比较对象，不承担打开编辑。
- **原因**：横向更接近摄影序列阅读，网格更适合总览；把“选择比较”与“打开工作副本”分离可以减少误操作。
- **未选方案**：只保留网格、用分页代替滚动、在 Compare 同时放大所有历史版本、自动生成不可修改的版本名称。
- **以后何时重看**：用户无法发现滚动条/箭头、频繁在双视角中迷失选择状态，或把版本包误认为打开编辑入口时。

### 结果

- **已完成**：改动意见2的全部实现、自动测试、四状态视觉验收和说明文档更新；
- **未完成/已知问题**：双视角与版本包尚未经过真实用户任务测试；版本管理仍只有内存状态；
- **下一步**：用 6–20 张序列测试横向阅读、视角切换和三版本比较，记录滚动方式、命名习惯与版本包点击预期。

## 2026-08-18 · Session 004 · 根据反馈收敛核心原型

**阶段**：Phase 0 用户验证<br>
**状态**：completed<br>
**关联 Issue/PR**：无；反馈来源为 prototypes/photoflex-core-prototype/comment.md

### 本次目标

根据第一轮产品反馈，把三方案原型收敛为单一 B 方案，并验证 Pool、Sequence 拖曳与星标版本比较的新交互是否完整可运行。

### 开始前

- **为什么现在做**：方案 B 的视觉方向已经明确，继续保留 A/C 会干扰下一轮访谈；Pool、Sequence 和 Compare 的旧结构也不能回答最新问题。
- **成功标准**：comment.md 的每条修改要求都有可点击行为和自动断言；复杂页面完成真实渲染检查。
- **明确不做**：不建立正式产品架构、不添加持久化、不读取真实照片、不把本轮产品反馈写成真实用户验证结论。

### 实际过程

- 删除 A/C 渲染与底部方案切换器，只保留 B 的深色沉浸方向，并将页面背景改为纯色；
- 将顶部导航改为三个大阶段按钮：Contact Sheet、Sequence + Pool、Compare；
- 删除当前意图、可见状态检查器与 Resume 页面；
- Contact Sheet 在加入 Pool 后清空临时选择，Pool 照片改为灰阶状态；从 Pool 删除后恢复彩色和可选择状态；
- 合并 Pool 与 Sequence：右侧 Pool 固定两列，勾选/反选与左侧 Sequence 双向同步，Sequence 不限制张数；
- 为 Sequence 加入浏览器原生拖曳排序；
- Compare 改为两个放大的纵向版本，不显示差异统计；每个版本拥有独立 Memo 和星标按钮；
- 首个版本自动成为星标基准；之后只比较星标版本与最新工作版本；打开历史版本会返回 Sequence，并在保存时生成新版本而不是覆盖；
- 更新 README 的启动方式、访谈脚本、验收状态 URL 和三张新预览，删除旧 A/B/C 截图。

### 验证

- **语法检查**：app.js 与 smoke-test.js 均通过 node --check；
- **自动流程**：smoke-test.js 覆盖单一 B 方案、Pool 灰阶与删除恢复、Pool ↔ Sequence 双向选择、拖曳排序、两版本 Compare、Memo、星标基准和版本工作副本；
- **视觉检查**：Chrome 无界面渲染 Contact Sheet、Sequence + Pool、Compare 三个 1440×1000 状态，未发现关键重叠或横向溢出；
- **调试记录**：两次测试失败分别来自身份定位属性和测试预设顺序错误；修正测试定位与拖曳场景后通过，未用跳过断言掩盖问题。

### 决策与权衡

- **决定**：方案 B 成为当前唯一研究方向；首个版本自动打星；版本编辑采用不可变工作副本。
- **原因**：减少比较噪音，同时保留“总有一个稳定基准”和“历史版本不被覆盖”的产品假设。
- **未选方案**：继续保留三方案切换、Pool 与 Sequence 分成独立页面、显示 Added/Removed/Moved 数据、保留 Resume。
- **以后何时重看**：下一轮真实用户无法理解自动打星、双向选择或工作副本时；Resume 是否回归仍需单独用户证据。

### 结果

- **已完成**：comment.md 全部原型修改、自动回归、三状态视觉检查与访谈说明更新；
- **未完成/已知问题**：原生拖曳尚未验证触控设备和完整键盘等价路径；本轮没有真实用户任务数据；
- **下一步**：用单一 B 方案执行 3–5 场任务测试，重点记录灰阶含义、拖曳放置预期、自动打星理解和版本工作副本心智模型。

## 2026-08-18 · Session 003 · 核心工作流可点击原型

**阶段**：Phase 0 用户验证<br>
**状态**：completed<br>
**关联 Issue/PR**：无；这是一次性研究原型，不是产品代码

### 本次目标

建立可以交给招募用户操作的核心原型，验证 Contact Sheet → Pool → Sequence → v1 → 修改 → v2 → Compare → Decision → Resume 是否可理解，并比较三种信息架构。

### 开始前

- **为什么现在做**：用户工作流假设已完成第一轮验证，需要用可操作界面观察真实任务行为，而不是继续只讨论文字需求。
- **成功标准**：核心路径可点击完成；A/B/C 三种结构共用相同状态；原型可单命令启动；访谈者有明确任务脚本。
- **明确不做**：不创建正式 Tauri/React 产品工程，不读取真实照片，不实现持久化、RAW、代理生成、数据库或云服务。

### 实际过程

- 新建 prototypes/photoflex-core-prototype/ 独立原型目录；
- 建立 A 工作台、B 沉浸画布、C 决策卡组三种可通过 ?variant=A|B|C 切换的结构；
- 实现选择照片、加入 Pool、建立 Sequence、保存 v1、修改并保存 v2、并排比较、差异摘要、记录决定和 Resume 恢复现场；
- 在界面中持续显示 stage、selection、Pool、Sequence、versions、decision、lastAction 和 nextAction，便于访谈观察；
- 加入底部方案切换器、左右方向键切换、重置演示和内存状态提示；
- 编写启动说明、访谈脚本、观察字段、原型边界和自动 smoke test；
- 生成并检查 A/B/C 三张真实渲染预览。

### 验证

- **语法检查**：node --check prototypes/photoflex-core-prototype/app.js 通过；
- **自动流程**：node prototypes/photoflex-core-prototype/smoke-test.js 通过，覆盖选择 → Pool → Sequence → v1 → v2 → Compare → Decision → Resume 和 A/B/C 切换；
- **启动检查**：本地静态服务返回 HTTP 200；
- **视觉检查**：Chrome 无界面渲染 A/B/C 均成功，1440×1000 下无关键布局溢出；
- **工具问题**：浏览器插件运行时无法启动，改用本机无界面浏览器做本地文件渲染；不影响原型运行结论。

### 决策与权衡

- **决定**：三个方案共用同一套数据和状态，只改变信息层级与页面结构。
- **原因**：访谈比较的是界面结构，不应让不同数据或不同功能干扰判断。
- **未选方案**：Figma 静态连线、直接建立正式前端工程、只做一种高保真方案。
- **以后何时重看**：完成首轮 3–5 位用户任务测试后，根据停顿、误解和恢复时间收敛为一个方向。

### 结果

- **已完成**：PH0-UX-04 的一次性可点击核心原型、三方案预览、访谈说明和自动状态测试；
- **未完成/已知问题**：尚无真实用户原型测试数据；真实 500 张规模、拖拽排序、完整键盘路径、索引失败状态和持久化均未验证；
- **下一步**：按 README 脚本先进行 3–5 场不解释术语的任务测试，记录任务完成、停顿点、预期行为和 Resume 恢复时间，再决定 A/B/C 的收敛方向。

### 决策与权衡

#### D-001：核心楔子

- **决定**：MVP 核心是 Look Hard + 多序列版本 + A/B 比较 + 修改理由 + 上下文恢复。
- **原因**：这是相对 Lightroom + PPT/Milanote 最可能产生明显优势的闭环。
- **未选方案**：从 DAM、通用白板、AI 或社区开始。
- **重看条件**：5 位以上真实用户无法证明多版本序列痛点。

#### D-002：桌面与本地优先

- **决定**：核心产品是本地桌面应用，原片只读引用；云端与 AI 可选。
- **原因**：照片规模、未发表作品隐私、离线需求和现有 Lightroom 工作流。
- **未选方案**：首版浏览器 SaaS、默认上传原图。
- **重看条件**：目标用户明确更需要跨设备协作，且愿意上传代理资产。

#### D-003：Tauri 暂定，保留 Electron fallback

- **决定**：暂定 Tauri 2 + React/TypeScript，但先进行两周技术反转测试。
- **原因**：Tauri 更符合轻量、文件权限和 Rust 后台任务；Electron 更易开发且渲染一致，因此不能在未验证时排除。
- **未选方案**：直接锁死某个框架。
- **重看条件**：六项技术门中有两项无法稳定通过。

#### D-004：版本用不可变完整 snapshot

- **决定**：MVP 保存完整序列 snapshot，并保留轻量事件差异。
- **原因**：序列规模有限；完整 snapshot 更容易恢复、比较、测试和导出。
- **未选方案**：仅存 patch、完整 event sourcing、自动 branch merge。
- **重看条件**：真实项目版本量导致不可接受的空间或性能问题。

#### D-005：RAW 不进入 P0

- **决定**：P0 以 Lightroom/JPEG 代理和常见渲染格式为主；RAW 只读预览放 P1。
- **原因**：RAW 解码、色彩和相机兼容会显著扩大首版风险，而目标用户已有 Lightroom。
- **未选方案**：首版直接显影所有 RAW。
- **重看条件**：用户测试显示没有 RAW 直读就无法采用产品。

#### D-006：AI 不作为 MVP 依赖

- **决定**：P0 的摘要、检索和恢复在无 AI 情况下成立。
- **原因**：避免网络、成本和艺术判断污染核心价值。
- **未选方案**：AI 自动选图、命名主题或生成最佳序列。
- **重看条件**：核心成立后，再验证文本研究、会话摘要与本地检索。

### 结果

- **已完成**：产品与技术企划、开发路线、日志制度。
- **未完成/已知问题**：没有用户访谈数据、没有技术 benchmark、没有代码或安装包；所有技术选择仍属于待验证方案。
- **下一步**：开展 Phase 0，而不是直接实现完整产品。
